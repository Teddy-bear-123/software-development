Why Version Control?

Good old days when we were using floppy disks to save our work…

💾 Local Version Control

  • A "database" of changes, on one machine
Now — how do you share it with someone else?

🖥️ Centralized Version Control

  • One central server stores the "database"
  • Clients check out files from the server
  • CVS, Subversion…
What if the server is down?

🌐 Distributed Version Control

  • Every client has a full copy of the "database"
  • Clients can work offline
  • Clients can share changes directly with each other
Git, Mercurial…

The Three States

Working directory

The files you're editing.

Staging area

What goes into the next commit.

git add: working dir → staging. git commit: staging → repository, "permanently" (see rewriting history, later).

Everyday Commands

git init                  # start a new repo
git status                # what's changed, what's staged
git add <path>            # stage a change
git commit -m "message"   # record staged changes
git log --oneline         # history
git diff                  # unstaged changes
git diff --staged         # staged changes

Branches

🌿 What's a branch?

  • Just a movable pointer to a commit
  • Cheap to create, cheap to switch
  • This is what makes parallel, independent work possible
git branch feature-x      # create
git switch feature-x      # move to it
git switch -c feature-y   # create + move

git branch — Create a Branch

$ git branch testing
A new pointer, testing, is created — HEAD still points to master.

git switch — Move the Pointer

$ git switch testing
HEAD now points to testing — the working directory updates to match.

git commit — Advance the Branch

$ git commit -a -m "made a change"
The testing branch moves forward. master is untouched — HEAD follows whichever branch is checked out.

Merging Branches

git switch master
git merge iss53

Merging & Conflicts

⚠️ When it happens

Two branches changed the same lines of the same file — Git can't guess which you want.

<<<<<<< HEAD
what you have
=======
what the other branch has
>>>>>>> other-branch
Fewer, smaller conflicts come from: committing often, pulling often, short-lived branches, and pull requests — exactly the situation the Day 2 merge session is designed to put you in on purpose.

Rebasing

🔄 An alternative to merging

  • Replays one branch's commits on top of another
  • ✅ pro: keeps history linear
  • ⚠️ con: rewrites history — risky once pushed
git checkout experiment
git rebase master
git checkout master
git merge experiment

Remotes: Fetch, Merge, Pull, Push

git fetch

Downloads what's new into your local repo — working copy unchanged yet.

git merge

Combines that into your working copy — same merge as any other.

git pull

Both in one command — a conflict can appear with no separate warning step.

git push

The only one going the other direction.

Rewriting History — Why It's Risky

git commit --amend      # fix the most recent commit
git rebase -i HEAD~3    # rewrite the last 3 commits interactively
Rule of thumb: only rewrite history nobody else has fetched yet. Once pushed or pulled, your history and theirs no longer agree — Git refuses a normal push, and their copy keeps the old commits regardless of what you do to yours.

Live Demo: "Deleted" ≠ "Gone"

The mistake we actually made building the data-challenge repo: 5 generated .npy files committed straight into the seed commit.

1️⃣ Plain rm

Only changes the working directory. git status still shows the file as tracked-but-deleted.

2️⃣ git rm + commit

Gone from HEAD — not from history. git log -- file still finds it.

3️⃣ Interactive rebase is what actually removes it from history — rewrite the commit that introduced it. git rebase -i --root, edit, git rm, commit --amend, rebase --continue.
The catch: only works because nobody fetched our mistake yet. Fixing it for real needs --force-with-lease — and anyone who already pulled still has the file.

.gitignore: Preventing This Next Time

# .gitignore
__pycache__/
*.pyc
.venv/
data/frames/          # generated, not source — regenerate, don't commit
.env
*.pem
*_token
credentials.json

⚠️ Only affects untracked files

Already committed? Also need git rm --cached <path> once.

🚫 Not a security boundary

A leaked credential must be revoked/rotated — history cleanup alone doesn't undo a clone that already happened.

GitHub: What It Adds on Top of Git

🐙 Platform

Hosts repos, adds issue tracking, PRs + review, Actions (CI/CD), Pages, Container Registry.

📖 Vocabulary

  • Repository — a project's Git history, hosted
  • Fork — your own copy of someone else's repo
  • Issue — tracks a bug, task, or question
  • Pull request — "please merge this branch into that one"

Roles: Developer, Reviewer, Maintainer

GitHub's real permission levels: Read < Triage < Write < Maintain < Admin — not a simplification.

RoleLevelDoes
DeveloperWritePushes branches, opens PRs, does the coding — most people on a team
ReviewerTriageComments, requests changes, approves — cannot push or merge
MaintainerMaintainMerges approved PRs, manages branch protection — the gatekeeper
Everyone plays more than one role over the two days. Who's maintainer for the shared upstream repo gets decided for real at the Day 1 tag-up.

Branching Strategies

A few common conventions for organizing branches on a shared repo:

  • Gitflow — most complex
  • GitHub flow — simplest
  • GitLab flow — most common?
  • GitLab flow, alternative

Gitflow

The most complex: long-lived develop, release, and hotfix branches alongside main.

GitHub Flow

The simplest: main is always deployable, every change is a short-lived branch off it. What this course uses.

GitLab Flow

Possibly the most common in practice: GitHub flow plus environment branches (e.g. staging, production).

GitLab Flow — Alternative

A variant using release branches instead of environment branches.

Workflow the data challenge: GitHub Flow

  • ✓ main is always deployable
  • ✓ Every change happens on a short-lived branch off main
  • ✓ Open a PR early — where discussion happens, not just a final gate
  • ✓ Review, address feedback, merge, delete the branch
Deliberately the simplest strategy — simple enough to run with a repo you've never seen before, exactly the situation at tonight's tag-up.

Reproducibility vs. Replicability

ReproducibilityReplicability
NatureTechnicalScientific
QuestionDone right?The right thing to do?
AnswerStraightforward — yes/noDifficult to judge — it depends…

There's a cost to reproducibility — match the effort to what the result is for. Full talk: Konrad Hinsen's seminar on reproducibility.

What's a Computation, Really?

A computation is a mapping from input bits to output bits — "meaning" is a human overlay, not something the computer knows.

Nothing Here Is Smooth

A 1-bit change in the input can cause an outsized change in the output. "I used the same code" ≠ "I got the same result."

Data and Code

Split the input side in two: what varies run to run is data, what should stay fixed is code — but code is just more bits going into the same box, nothing structurally different about it.

…and Environment

A third, usually invisible input: the environment (interpreter, libraries, OS, hardware) — the whole reason this session exists.

Whose Problem Is Which Layer?

dataprogramenvironment
Scientist's viewmy researchmy colleagues' codestuff I don't care about
Engineer's viewmy colleagues' datamy codestuff I don't care about
What's actually truezeros and onesan interpretation of the dataan interpretation of the program
Everyone treats someone else's layer as "not their problem." Managing environments makes that explicit instead of leaving it assumed.

How to Manage Environments?

Comparing the Tools

ToolReproducibilityIsolationBest for
CondaLimited (resolver drift)Weak — shares hostDay-to-day dev, prototyping
Conda + conda-lockBetter (hashes, pinned)WeakShared dev environments
DockerHigh, if base image pinnedStrong — undeclared deps fail loudlyDeployment, CI
Guix/NixBitwise exactStrongest — sandboxedPublication-grade research
Isolation isn't just a nicety — it's what forces undeclared dependencies to surface, and it's a security boundary. Do you need bitwise reproducibility, or is replicability enough? Usually the second.

Conda / Miniforge

⚠️ Watch out

Anaconda's defaults channel is under a commercial license — many institutions restrict it. Use conda-forge instead (what Miniforge ships by default).

conda create -n myenv python numpy pandas
conda activate myenv
conda install matplotlib
conda env export --no-builds > environment.yml
conda env create -f environment.yml -n myenv2
conda env remove -n myenv

Spot the Problem

channels: [defaults]
dependencies:
  - python=3.7
  - numpy=1.18.5
  - pandas=1.0.5
  - pip:
      - scikit-learn==0.22
defaults channel (license) · hard-pinned to old versions (no security updates, brittle) · scikit-learn via pip when conda-forge has it too.
Fix: conda-forge channel, version ranges (python>=3.10,<3.13), let conda resolve.

Containers: Docker

📦 What it buys

  • Packages OS libraries and code together
  • Isolation + portability — same image, any machine
  • Not magic either: pin the base image digest
FROM python:3.11-slim
RUN pip install numpy matplotlib
COPY . /app
WORKDIR /app
CMD ["python", "-m", "astrolab.pipeline"]
docker build -t astrolab .
docker run --rm astrolab

Technical Debt

Types of Technical Debt

Code debt

Copy-pasted logic; one fix needs applying in N places.

Design debt

Hardcoded paths/thresholds; breaks elsewhere.

Testing debt

A change silently breaks old behavior.

Documentation debt

Future-you loses an afternoon.

Why Testing & Docs Come First

Code and design debt get paid down by review and refactoring — but refactoring without tests is just changing things and hoping.

Tests

"I refactored this, I think it still works" → "…and the suite proves it."

Docs

"Why does this do that?" from archaeology → five-second lookup.

Why Test Early

The same typo in a formula: a minute in code review, an hour in system testing, hours plus an emergency release in production. Nothing about the bug changed — only how much got built on top of it.

Docs & Tests: Two Halves of the Same Idea

📝 Docstring

The specification you want — what a function should do, for which inputs.

✅ Unit test

Code that checks the function actually behaves that way.

doctest is the extreme case: the same lines are the spec and the check — they can't drift apart.

Docstring → Doctest → API Docs

def factorial(n):
    """Return the factorial of n, an exact non-negative integer.

    >>> [factorial(n) for n in range(5)]
    [1, 1, 2, 6, 24]
    >>> factorial(-1)
    Traceback (most recent call last):
        ...
    ValueError: n must be >= 0
    """
    if n < 0:
        raise ValueError("n must be >= 0")
    result = 1
    for factor in range(2, n + 1):
        result *= factor
    return result
Executable documentation — the example in the docstring is the test. Docs can't quietly drift from the code.

Unit Tests Are More Than Testing

  • ✓ Forces you to think through your internal design
  • ✓ Forces a spec for internal APIs nobody would write down otherwise
  • ✓ A green suite is permission to refactor without re-litigating "does this still work?"
  • ✓ Encodes corner cases already fought through
  • ✓ Outlives the implementation — a spec you can carry into a rewrite
Writing code without testing it is no engineering, it's just writing code.

def test_constructor(self):

    self.assertEqual(p.get_x(), 0.0)
    self.assertEqual(p.get_vx(), 2.0)

Manual mock

class ManualMockBackend(StorageBackend):
    def pread(self, offset, size):

unittest.mock

Payoff: call pread(0,5) twice, assert the mock was called once — the second read must be served from cache. A real backend would make this slow and awkward to write.

Bonus: a Real Bug Hunt With MALT

Integration test

ctest -V — something's off, somewhere in the whole program.

Unit tests

ctest -R {TEST_NAME} -V — one file, one function, a five-minute find.

Conclusion: Write Them, But Write Them Well

def test_elastic_collision(self):
    p1, p2 = Particle(0.0, 1.0), Particle(5.0, -1.0)
    result = elastic_collision(p1, p2, dt=10)
    self.assertIsNotNone(result)   # checks nothing about the physics
Passes, coverage counts every line touched, CI goes green — and would pass exactly as well if the function returned garbage.
Relevance first, coverage second. 60% coverage of tests that check the right answer beats 100% of tests that check nothing.

Workflow Control

Why Automate?

The demo effect: it works perfectly right up until you run it in front of an audience. "It ran here a minute ago" ≠ "it reliably runs."

DevOps & CI/CD

DevOps

Treat "build, test, release, operate" as one continuous, shared responsibility — not "dev throws it over the wall."

CI/CD

CI: same checks, same clean environment, automatically, every push. CD: extend that to shipping the result.

The Automated Replacement

Same shape as the manual version, stage for stage — the difference is every arrow after "push" runs itself.

pixi: Project-Scoped, Lockfile-Native

Why beyond Conda

  • Env lives in the project (pixi.toml), not ~/.conda/envs
  • Tasks: pixi run test — everyone, and CI, run the same invocation
  • Lockfile always, not an opt-in step
  • Multi-platform pins in one file
pixi init astrolab -c conda-forge
cd astrolab
pixi add numpy matplotlib
pixi task add test "pytest"
pixi run test
pixi run python -m astrolab.pipeline

GitHub Actions, Mechanics

📄 Workflow

YAML in .github/workflows/, triggered by events: on: push, pull_request…

⚙️ Jobs & steps

Jobs run in parallel on a fresh runner. uses: a reusable action, run: a shell command.

🔒 Secrets

secrets.GITHUB_TOKEN auto-provisioned per run — never in a commit.

📊 Actions tab

Every run, green or red, full logs per step.

Minimal Workflow

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: python -m doctest main.py -v

GHCR: Picking Back Up From Session 2

  docker:
    runs-on: ubuntu-latest
    needs: test              # only if tests passed
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:latest
            ghcr.io/${{ github.repository }}:${{ github.sha }}

  • #12Real-sky bonus — astroquery/SkyView call, disk caching, --real flag
Why the conflict is the point: pipeline.py and README.md get touched by nearly every task, on purpose. Real projects don't hand every team a private file.

Fix Roles & Workflow — Decide Now, Not Tomorrow

👑 Maintainers

2–3 people get Maintain, run Day 2's merge session.

👀 Reviewers

Everyone reviews ≥1 other team's PR before Day 2.

🌿 Branch naming

issue-<n>-<short-slug> so 6+ teams' branches don't collide.

⚔️ Conflict ownership

Agree now who resolves a conflict when two PRs touch the same lines.

Implement the tasks

Each team, in their fork: implement the claimed task(s), organized however the team likes internally, then open a PR from the fork to upstream main.

Merge Session: Finished Teams First

gh pr checkout <number>        # fetch the fork's branch locally
# read the diff, check CI is green, confirm the review bar
gh pr merge <number> --merge
This is integration time, not more implementation time. Work down the PR list in the order PRs went green — not alphabetically or by claim order.

Demo: Resolving a Real Merge Conflict

gh pr checkout <number>
git fetch upstream main
git merge upstream/main            # conflict markers appear
# resolve <<<<<<< / ======= / >>>>>>> by hand
git add pipeline.py

Exactly Session 1's "Merging and conflicts" mechanic, showing up for real, between two teams' independent work.

Finished Teams: Don't Sit Idle

Once your PR is merged, go help a team still working — debug, pair, get their branch mergeable. The room's total "stuck" count is what should be dropping, not just the merged-PR count.

Wrap-Up: Merge What's Ready

Keep merging finished PRs. If some teams haven't finished, that's fine — stop there. Don't extend the coding time to force a finish.

Capture 2–3 takeaways per team — the same questions a real retro asks after a real sprint.
